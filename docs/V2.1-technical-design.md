# 0. 设计决策摘要

本版本基于既有 V2 方案做关键修正：不再依赖公司内部完整 OA
源码或离职后无法访问的企业接口，而是自行实现可独立运行的 Enterprise
Approval
Service（企业审批服务），并以主数据变更审批作为一期真实业务原型。

Agent 层通过 ApprovalAdapter 与审批后端解耦；未来如接入真实 OA、BPM
或企业审批平台，仅替换 Adapter，不改 Agent Graph、Tool Contract、Task
State 与前端交互协议。

## 0.1 三个项目的最终定位

| **项目**                  | **定位**             | **一期核心能力**                                                    | **面试价值**                                                |
|---------------------------|----------------------|---------------------------------------------------------------------|-------------------------------------------------------------|
| Enterprise Approval Agent | 执行型业务 Agent     | 自然语言变更主数据、校验、Diff、提交审批、状态查询、撤回、审批/退回 | Tool Calling、Agent Loop、State、HITL、权限、幂等、业务后端 |
| Contract Review Agent     | 文档智能 / RAG Agent | 合同解析、分类、知识检索、风险审查、模板核对、报告生成              | RAG、Structured Output、文档处理、Evaluation                |
| DSH Multi-Agent Platform  | 多智能体运行与协作层 | Registry、Router、Handoff、Task Context、Trace、MCP                 | Multi-Agent、Orchestration、Context Engineering、平台化     |

# 1. 一期业务目标与边界

## 1.1 一期必须跑通的三个 Demo

1\. 主数据变更审批：用户说“把供应商 A 的付款方式改成月结 30
天并提交审批”，Agent 完成读取、字段抽取、规则校验、Diff
展示、人工确认与提交。

2\. 审批上下文续接：用户说“撤回我刚才提交的申请”，系统从 Task State /
最近审批上下文解析目标审批单，校验状态并在确认后撤回。

3\. 跨
Agent：用户上传采购合同并说“如果没有高风险问题就发起审批”，Contract
Agent 审查后 Handoff 给 Approval Agent。

## 1.2 一期明确不做

- 完整 BPMN 引擎

- 复杂组织架构同步

- 十几个业务 Agent

- 模型训练 / 微调

- Agent Marketplace

- 分布式任务集群

- 复杂 RBAC 管理后台

- 自动执行 CRITICAL 风险动作

- 多模型成本路由优化

## 4.2 Agent 工作台组件

- ChatMessage：user / assistant / system / error 四类消息。

- StreamingMessage：增量 Token 渲染。

- ToolCallCard：展示 Tool 名、状态、耗时；默认不暴露敏感参数。

- ApprovalPreviewCard：展示审批对象、Before/After
  Diff、风险提示和确认按钮。

- HumanConfirmModal：高风险动作二次确认；确认动作绑定 action_id 与
  confirmation_token。

- TaskTimeline：展示当前 Agent、Tool、Waiting User、Waiting
  Confirmation、Completed。

- CitationPanel：显示制度 / 合同知识引用。

- ContractRiskTable：风险等级、条款、问题、建议、引用。

- TemplateDiffPanel：标准模板与当前合同的差异。

- TraceWaterfall：Agent 与 Tool Span 时间线。

## 4.3 前端状态管理

使用 Pinia；不要把所有服务端数据长期复制到 store。store
只保存跨组件状态，页面级服务端数据通过 api/composable 管理。

stores/  
├─ auth.ts \# 当前用户、角色、token  
├─ session.ts \# 当前会话  
├─ task.ts \# 当前 task 状态、事件、waiting action  
└─ ui.ts \# 纯 UI 状态

## 4.4 前端 Task 状态映射

| **后端状态**         | **前端行为**                                                |
|----------------------|-------------------------------------------------------------|
| created / planning   | 显示“正在理解任务”                                          |
| running              | 展示 Agent / Tool 执行时间线                                |
| waiting_user         | 显示 Agent 问题并启用输入框                                 |
| waiting_confirmation | 展示结构化确认卡片；普通聊天输入不作为确认                  |
| completed            | 展示结果、审批单号、审查报告等                              |
| failed               | 展示友好错误 + request_id；允许重新发起而不是盲目重复写操作 |
| cancelled            | 任务结束，不继续消费流                                      |

## 4.5 SSE / 流式协议

使用服务端 SSE 语义，但前端优先封装 Fetch + ReadableStream，以便携带
Authorization Header。所有事件都包含 task_id、event_id、timestamp。

event: tool.completed  
data: {  
"event_id": "evt_123",  
"task_id": "task_001",  
"type": "tool.completed",  
"payload": {  
"tool_name": "validate_master_data_change",  
"status": "success",  
"latency_ms": 42  
}  
}

## 4.6 前端交互安全约束

- HIGH 风险动作只能通过确认卡片触发 confirm
  API，不能把“用户说确认”直接当作提交授权。

- 不在前端保存 API Key、系统 Prompt、完整 Tool Secret。

- 错误提示展示 request_id，不展示 Python 堆栈。

- Approval Diff 必须从后端结构化数据渲染，不根据 LLM 文本猜测。

# 6. 认证与权限模型

## 6.1 Demo 用户

为保证离职后仍可演示，一期实现独立登录与角色体系，不依赖公司
SSO。密码仅用于本地 Demo，必须加密哈希存储。

| **用户**   | **角色**   | **主要权限**                                            |
|------------|------------|---------------------------------------------------------|
| applicant  | APPLICANT  | 查看/修改自己的主数据草稿、提交、查询、可撤回状态下撤回 |
| manager    | APPROVER   | 查看分配给自己的待审批、通过、退回                      |
| data_admin | DATA_ADMIN | 第二审批节点、查看主数据规则和最终审批                  |
| admin      | ADMIN      | 开发演示管理；不自动赋予 Agent 无限业务权限             |

## 6.2 Agent 身份传播原则

acting_user_id 与 roles 来自认证上下文，由 Tool Executor 注入，LLM
不允许在 Tool 参数中自由指定任意 user_id。这样防止 Prompt Injection
通过伪造用户 ID 越权。

# 7. Approval Service 领域设计

## 7.1 主数据模型

一期使用 Supplier（供应商）作为主数据示例，但实体模型保留
entity_type，后续可扩展 Customer、Material 等。

Supplier 示例字段：  
- supplier_code  
- supplier_name  
- payment_term  
- bank_account_masked  
- tax_id_masked  
- status  
- version

## 7.2 审批状态机

DRAFT  
└─ submit → SUBMITTED  
SUBMITTED  
├─ start_review → APPROVING  
└─ withdraw → WITHDRAWN  
APPROVING  
├─ approve(node not last) → APPROVING(next node)  
├─ approve(last node) → APPROVED  
├─ return → RETURNED  
└─ withdraw(if policy allows) → WITHDRAWN  
RETURNED  
└─ edit → DRAFT  
  
Terminal: APPROVED / WITHDRAWN

## 7.3 状态转换权限矩阵

| **动作** | **允许来源状态**      | **角色**          | **是否 HITL** | **幂等**     |
|----------|-----------------------|-------------------|---------------|--------------|
| submit   | DRAFT                 | APPLICANT         | 是            | 必须         |
| withdraw | SUBMITTED / APPROVING | 原申请人          | 是            | 必须         |
| approve  | APPROVING             | 当前节点 APPROVER | 是            | 必须         |
| return   | APPROVING             | 当前节点 APPROVER | 是            | 必须         |
| edit     | DRAFT / RETURNED      | 原申请人          | 否            | 更新用乐观锁 |
| read     | 有权限记录            | 按数据权限        | 否            | 不要求       |

## 7.4 轻量 Workflow Definition

一期不实现 BPMN。使用版本化 JSON 定义审批节点，提交时记录
workflow_version，后续配置修改不影响已运行实例。

{  
"code": "supplier_change",  
"version": 1,  
"nodes": \[  
{"key": "manager_review", "role": "APPROVER"},  
{"key": "data_admin_review", "role": "DATA_ADMIN"}  
\]  
}

## 10.2 Context Builder

统一 build_context(state, agent_definition)，禁止每个 Agent
自己随意拼接所有历史消息。

Context =  
System Prompt  
+ Agent Goal / Allowed Tools  
+ Current Task State (structured)  
+ Relevant Short/Long Memory  
+ Recent Messages  
+ Last Tool Results  
+ Current User Input

必须有 Token Budget；超预算优先保留 State 与最近 Tool
Result，再摘要历史，不允许丢失 pending_confirmation 或关键审批 ID。

# 11. Tool 基础设施

## 11.1 ToolDefinition

class ToolDefinition(BaseModel):  
name: str  
description: str  
input_model: type\[BaseModel\]  
output_model: type\[BaseModel\]  
risk_level: Literal\["LOW","MEDIUM","HIGH","CRITICAL"\]  
required_permissions: list\[str\]  
timeout_seconds: int  
max_retries: int  
idempotent: bool  
allowed_agents: list\[str\]

## 11.2 Tool Executor 固定执行管线

1\. Resolve Tool  
2. Validate agent allowed_tools  
3. Validate Pydantic input  
4. Inject acting identity from auth/task context  
5. Permission check  
6. Risk / confirmation check  
7. Idempotency lookup (write tools)  
8. Create trace span  
9. Execute with timeout  
10. Retry only if policy allows  
11. Validate structured output  
12. Persist tool_run / audit  
13. Save idempotency result  
14. Return ToolResult

# 16. Human-in-the-loop 与 Confirmation Token

确认不是一句自然语言文本，而是服务端生成的 pending
action。前端展示结构化预览，用户点击确认后提交 action_id；后端验证
action 仍有效、资源版本未变化，再签发/消费一次性 confirmation token。

ConfirmationRequest:  
- action_id  
- task_id  
- tool_name  
- resource_id  
- resource_version  
- summary  
- expires_at  
- confirmation_token(one-time)

# 17. Idempotency / Retry / Timeout

## 17.1 幂等

submit / withdraw / approve / return 等所有写操作都要求
Idempotency-Key。key 与 action + resource 绑定；相同 key
重放返回第一次结果。

## 17.2 Retry

- 纯查询 Tool：默认最多 2 次指数退避重试。

- 写 Tool：只有幂等保障后才允许重试。

- 业务校验错误、权限错误、状态转换错误：绝不重试。

- LLM 结构化输出失败：允许有限 repair，不允许无限循环。

## 17.3 Timeout

每个 ToolDefinition 定义 timeout；Tool Executor 必须强制超时并产生
ToolResult error，Agent 根据 retryable 决定下一步。

一期优先复用已有知识库能力；本地独立运行时可用
pgvector。KnowledgeAdapter 对上暴露统一 search(query, filters, top_k)。

# 20. Memory 与 Context Engineering

## 20.1 三层 Memory

| **层**            | **内容**                                 | **存储**            | **一期** |
|-------------------|------------------------------------------|---------------------|----------|
| Working Memory    | TaskState / pending action / approval id | DB checkpoint       | 必须     |
| Short-term Memory | 最近对话摘要与必要消息                   | Redis/DB            | 必须     |
| Long-term Memory  | 稳定偏好或常用配置                       | PostgreSQL/向量检索 | 最小实现 |

## 20.2 Context Budget 策略

优先级：System/Guardrails \> Current State \> Pending Action \> Latest
Tool Result \> Recent Messages \> Relevant Memory \> Historical
Summary。

# 21. Guardrails 与安全

- 身份与权限永远来自服务端上下文，不能信任 LLM 生成的 user_id / role。

- Tool allowlist 按 Agent 限制，Router 不扩大权限。

- 敏感字段默认 Mask；Trace 不记录明文密码、token、完整银行账号。

- 外部文档视为不可信输入，文档中的“忽略系统指令”等文本不能修改系统权限。

- CRITICAL Tool 一期不提供给模型。

- 合同/制度引用与模型推断分开显示。

# 28. Definition of Done

- 审批后端可独立运行，不依赖公司网络或公司接口。

- Agent 所有业务动作必须通过 Tool Executor，不能绕开权限、幂等和审计。

- HIGH 风险操作必须走结构化 HITL。

- 前端可完整演示主数据变更 → Diff → 确认 → 提交 → 查询 → 撤回/审批。

- Contract Agent 可输出结构化风险与引用，并生成报告。

- Router/Handoff 可完成“合同无高风险则发起审批”。

- 完整 Trace 可查看 Agent、Tool、耗时、Token、错误。

- 至少一套真实 Evaluation Dataset 与自动报告。

- 所有核心路径有自动化测试，CI 通过。

- README 能从空环境启动；敏感配置只存在 .env.example 占位。
