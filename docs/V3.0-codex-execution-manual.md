# 0. 手册目的

本手册不是需求文档，也不是技术方案说明。它定义 Codex 如何按 V2.1
实施、每次允许改什么、完成后必须交付什么，以及架构设计者 / Reviewer
如何验收。

核心工作方式：Codex 负责 Implementation（实现），你负责
Product/Architecture Decision（需求与架构决策），ChatGPT 作为
Architecture Reviewer（架构与代码评审辅助），对 Codex 的
diff、commit、测试结果和问题进行 Review。

# 2. 仓库根目录 CODEX.md 必须包含的规则

\# CODEX.md - mandatory working contract  
  
1. Read docs/V2.1-technical-design.md and
docs/V3.0-codex-execution-manual.md before changes.  
2. Work on exactly one approved TASK/phase scope at a time.  
3. Do not invent real company OA/SSO/knowledge APIs. Use Adapter +
Mock/local implementation.  
4. Do not bypass ToolExecutor for Agent business actions.  
5. Do not let LLM-provided identity/role override authenticated server
context.  
6. HIGH-risk actions require structured HITL.  
7. Write operations require idempotency where specified.  
8. No task is complete until tests and required checks pass.  
9. Do not silently change public API, DB schema, state machine, Tool
contract, or directory architecture.  
10. Any architecture deviation requires ADR proposal and explicit
approval.  
11. Never hard-code secrets; update .env.example with placeholders
only.  
12. Preserve existing passing tests. If behavior changes, explain why
and update tests intentionally.  
13. At task completion output: changed files, design decisions, commands
run, test results, migrations, known limitations, next recommended
task.  
14. Do not claim success if a command/test was not actually run.

# 7. Coding Standard - Backend

- 所有 public request/response、Tool input/output 使用 Pydantic
  Model，不传裸 dict 穿越多层。

- 领域状态使用 Enum；禁止散落魔法字符串。

- Async 只用于真实 I/O；不要把纯 CPU/纯逻辑函数机械 async 化。

- Repository 只负责持久化，不做 LLM/业务编排。

- Domain Service 不依赖 FastAPI Request 对象。

- 异常在边界转换为统一 Error Model；内部不使用 HTTPException
  传播整个领域层。

- 函数默认短小；超过约 60-80 行需检查是否职责过多。

- 业务规则必须有测试；状态机转换至少表驱动测试。

- 所有写操作考虑事务边界和并发版本。

# 8. Coding Standard - Frontend

- Composition API + script setup + TypeScript。

- API 类型统一放 src/types / src/api，不在组件内复制接口类型。

- 组件不直接拼后端 URL；统一 API client。

- Task 流式状态归一化，页面只消费状态，不解析随机文本判断状态。

- 确认按钮提交期间禁用，防止重复点击。

- Approval Diff、Risk、Trace 使用结构化数据渲染。

- 错误提示面向用户，Debug 细节放 Trace / console dev，不直接展示堆栈。

# 9. 数据库与 Migration 规则

- 任何表结构变化必须 Alembic migration；禁止只改 ORM 不生成 migration。

- Migration 必须支持空库 upgrade head；重要 migration 做 downgrade
  smoke。

- 生产式表使用 created_at/updated_at；必要时 version。

- 审批历史 append-only，不 UPDATE 历史动作。

- 敏感字段不写入 audit metadata 原文。

- Seed 数据独立 script，migration 不写 Demo 业务数据。

# 10. Prompt / Agent 变更规则

- Prompt 文件版本化；变更 Prompt 时同步 Eval。

- 新增 Tool 前先明确 risk / permission / idempotency / timeout。

- 增加 Tool 不代表自动暴露给全部 Agent；必须更新 allowed_tools。

- LLM 不负责确定性权限、余额、状态机合法性等规则。

- Agent Loop 必须存在 max_steps / termination guard。

- Structured Output 解析失败只允许有限 repair。

- 任何让 Agent 自动执行 HIGH risk 的提案默认拒绝，除非改 HITL
  设计并经批准。

# 19. Review 时最容易被 Codex 做错的 15 件事

1\. 把整个审批状态机写进 Router/API Controller。

2\. Agent 直接调用 Repository 或数据库。

3\. 让 LLM 输出 user_id / role 并据此鉴权。

4\. 把“确认”做成匹配用户文本 contains("确认")。

5\. 写 Tool 没有 Idempotency-Key。

6\. 所有异常都 retry。

7\. 把 Tool 参数/结果无脱敏全量写日志。

8\. Prompt 散落在代码里。

9\. Context 每轮塞所有历史聊天。

10\. Router 永远输出 Multi-Agent，过度编排。

11\. 只写 happy path 测试。

12\. 数据库表改了但没 migration。

13\. 前端从 assistant 文本解析“审批成功”。

14\. Eval 指标手填。

15\. README 声称做了 MCP/Memory/Trace，但代码只留空类。
